## 1. 背景与测试原理

### 1.1 MBIST 是什么

LB3 芯片的 P1 存储器系统（SRAM 分组 G0~G7、ROM 分组 G1~G5）在流片时植入了 **MBIST（Memory Built-In Self-Test，存储器内建自测试）** 电路。测试时测试程序（运行于 FPGA 平台，见 1.2 节）只需下发测试向量、提供电源和时钟，片上 BIST 控制器自动执行 March 等算法对存储器读写校验，输出：

- **Error Count**：错误计数（0~1000，饱和封顶）
- **Test Result**：测试结果字段，取值见 1.1.1
- **Fail Dump**：失败周期的逐 cycle 位图（txt 文件）

#### 1.1.1 Test Result 取值定义

| 取值 | 定义 | 发生环节 | 性质 |
|---|---|---|---|
| **Pass** | 测试正常执行且读出数据全部正确（Error Count = 0） | MBIST 算法执行后 | 有效数据点，芯片该项合格 |
| **Fail** | 测试正常执行但读出数据存在错误（Error Count > 0） | MBIST 算法执行后 | 有效数据点，芯片相关失败 |
| **ClockSetFail** | 测试程序向被测频率切换时**时钟配置失败**（时钟模块频率字写入/锁定未成功，见 1.2 节时钟配置机制），测试未真正执行 | 测试前置（时钟建立阶段） | **设备侧无效数据点** |
| **ReadError** | 程控电源回读的实测 VDDL 与设定值偏差超出容差，供电未达标，测试结果不可信 | 测试前置（电压建立/回读阶段） | **设备侧无效数据点** |

两类设备侧结果的共同特征：**失败发生在测试执行之前的环境建立环节，与被测芯片无关**。该数据点既不能证明芯片合格，也不能证明芯片失效，本质上是一个"没有测到"的空点。

#### 1.1.2 工具对四类结果的处理逻辑

| 结果 | 良率统计 | 失效分类 | Shmoo 矩阵 | 展示位置 |
|---|---|---|---|---|
| Pass | ✅ 计入通过 | — | ✅ 计入通过数 | — |
| Fail | ✅ 计入失败 | ✅ 参与分类 | ✅ 计入失败 | 失败明细 sheet |
| ClockSetFail | ❌ 不参与 | ❌ 不参与 | ❌ 计入失败(标红) | 日志/总览列/设备侧异常 sheet |
| ReadError | ❌ 不参与 | ❌ 不参与 | ❌ 计入失败(标红) | 日志/总览列/设备侧异常 sheet |

要点：

1. **不判 Fail**：ClockSetFail/ReadError 不是芯片缺陷，混入判定会把健康芯片误判为失效、低估良率；
2. **不产生异常类别**：芯片若仅有此类数据点、无真实 Fail，直接判 **Pass**，不设"设备异常"类别；
3. **保持可见**：数量显示在 CLI 日志（"设备侧无效数据点...仅供参考: N 个"）、总览"设备侧异常"列；明细记录在"设备侧异常" sheet（芯片/向量/频率/电压/结果），供测试人员核查是否需要复测或排查机台；
4. **芯片说明附带计数**：如 `Pass | 全部测试点通过 (+1 个ClockSetFail/ReadError数据点, 不参与判定)`，不影响类别归属；
5. **Shmoo 矩阵例外**：Shmoo 矩阵中该格点按"未通过"显示（红色），因为该点确实没有通过数据——但这是展示层面的保守处理，不参与良率判定。

### 1.2 测试系统架构（DFT Test Tool V3.1）

测试程序为 **DFT Test Tool V3.1（Linux CLI 版）**，基于 FPGA 平台而非传统 ATE 机台（详细文档见 `/yuna/Documents_for_read/md/LB3_DFT_TEST.md`）：

**硬件与链路**：

```
测试主机(Linux x86) ──SSH(paramiko)──▶ FPGA服务器(ARM Linux, sudo)
                                          │ PCIe XDMA 字符设备
                                          ▼
                                   Xilinx VCU118 开发板
                                   Virtex UltraScale+ XCVU9P
                                   ┌─────────────────────┐
                                   │ DFT 测试模块 (RTL)   │
                                   │ · 扫描链控制          │
                                   │ · 向量比较器          │
                                   │ · 错误计数器          │
                                   │ · DDR 控制器          │
                                   │ · 时钟管理(5路可编程)  │
                                   └─────────────────────┘
```

- **XDMA 通道**：`/dev/xdma0_user`（控制/状态寄存器，32-bit 读写）、`/dev/xdma0_h2c_0`（向量加载，主机→FPGA）、`/dev/xdma0_c2h_0`（结果回读，FPGA→主机）；
- **DDR 分区**：测试向量存 `0x00000000`（低 2GB），采样/捕获数据存 `0x80000000`（高 2GB），两区隔离防覆盖。

**关键寄存器**（经 `xdma0_user` 以 AXI-Lite 方式访问）：

| 偏移 | 寄存器 | 说明 |
|---|---|---|
| 0x00 | VECTOR_LINE_SIZE | 向量行数（= 文件行数 − 1，首行为 IO 模式字） |
| 0x04 | START | 测试启动（脉冲触发：写 1 → 0.5s → 写 0） |
| 0x08 | STATUS | 测试状态（轮询至 0 表示完成） |
| 0x14 / 0x18 | VECTOR/SAMPLE_DDR_ADDR | DDR 地址 |
| 0x1C | CLEAR_FIFO | FIFO 清除（写 3 → 延时 → 写 0） |
| 0x20 | ERROR_CNT | 错误计数器（只读，即 csv 中的 Error Count 来源） |
| 0x2C | IO_MODE_SEL | IO 模式选择（**取自向量文件首行**） |
| 0x208~0x35C | CLK0~4_FREQ/PHASE/DUTY | 5 路时钟配置（频率/相位/占空比） |

**时钟配置机制（Shmoo 频率轴的实现）**：板载时钟由 1200MHz 基准时频分产生，`频率 = 1200 / 分频字`。例如 25MHz → 分频字 48（0x30）、20MHz → 60（0x3C）。扫描测试时程序逐点写 CLK0_FREQ 寄存器并锁存（写 0x35C=0x3 生效）。**ClockSetFail 即该时钟配置环节失败**。

**单向量测试流程**（批量/扫描测试为其循环）：

```
清FIFO → XDMA加载向量到DDR → 写IO_MODE_SEL(向量首行) + VECTOR_LINE_SIZE
→ 写DDR地址 → START脉冲(1→0) → 轮询STATUS至0
→ 读ERROR_CNT写入CSV → (失败时)XDMA回读dump数据
```

**与本工具数据的关系**：DFT Test Tool 产出的 error_count CSV 与 dump 位图 txt（服务器端 `vector_dump_txt` hex 格式回读后转换），即本工具 2.1 节数据文件的上游来源；LB3 批次 csv 中的电压列（Set Voltage / Read VDDL）对应程控电源控制的扩展流程，ReadError 即电源回读超差。

### 1.5 向量文件格式

向量文件为纯文本，结构为"**首行 IO 模式字 + 逐周期激励数据**"：

```
0xB88E                                          ← 第1行: IO模式选择值(16进制)
0000...00010000000110                            ← 第2行起: 每行一个测试周期
0000...00010010000110                            （128位并行激励, 0/1对应通道电平）
...                                              （G0向量共 5937 行）
```

**首行：IO 模式选择值（IO Mode Select）**：

- 测试程序加载向量时，将首行值写入 FPGA 的 **IO_MODE_SEL 寄存器（偏移 0x2C）**，用于配置被测 IO 的驱动/比较模式（另有 IO_MODE_SEL1/2 寄存器 0x30/0x34 备用）；
- 16 进制表示，宽度不固定（12~32 bit，随向量类型而异）；
- **实测规律**（可用于快速核对向量归属，即 vecinfo"分组指纹表"的依据）：
  - 同分组向量的 IO 模式字高位（基值）相同，低位随算法/应力变体小幅变化：G0 基础 March = `0xB88E`，G0 全部 EMC 变体 = `0xB884`（差 0x0A）；G2 为 `0x15561` / `0x15557`；
  - 各分组基值互不相同（G0=0xB88E、G1=0x9DC8、G7=0x266A...），可作为分组指纹；
  - 同一分组的全部 EMC 码型（0000~1111）共享同一 IO 模式字——EMC 电源域组合由程控电源实现，与 IO 模式无关。

**激励数据（第 2 行起）**：

- 每行一个测试周期（cycle），128 位并行激励；
- 程序按 `vector_size = 总行数 − 1` 写入 VECTOR_LINE_SIZE 寄存器；向量以二进制分片形式经 XDMA H2C 通道加载到 DDR（每包 8192 行）；失败时 dump 长度 = `(总行数 − 1) × 16` 字节（每行 128 bit = 16 字节）；
- 典型向量长度：存储器向量约 4 000~15 000 cycle（G0=5937、G3_EMC=14911、RT_TYPE 修复向量最长达 15 239），ICLNetwork=9 058；
- 171 个向量总计约 130 万 cycle，25MHz 下纯执行仅约 0.1 秒——实际测试耗时主要在条件建立（时钟/电压/FIFO）、XDMA 向量加载与结果回读，这也是 Shmoo 全扫描（80 格点）需 30~60 分钟/颗的原因。

| 向量组 | 数量 | 算法/应力 | 针对故障模型 |

### 2.4 温度识别规则与分图逻辑（前置条件）

批次有单温度/双温度/无温度三种形态，工具按以下优先级识别每颗芯片的温度：

```
① 芯片子文件夹名后缀（权威来源）        PDK1_TT10_85 → 85°C, PDK1_TT02_-25 → -25°C,
                                        PDK1_TT02_0 → 0°C, PDK1_TT02(无后缀) → 见②③
② 批次文件夹名单一温度标记（兜底）      "…_85c_31pcs" → 85°C（仅当恰好识别出 1 个温度）
③ 都没有 → 常温
   ⚠ 批次名含多个温度但芯片无后缀 = 歧义 → 全部按常温处理并打印警告
```

批次名温度标记格式：`85c` / `125c`（数字+c）或 `temp-25` / `temp0`（temp+数字）。

**约定与行为**：

| 约定 | 说明 |
|---|---|
| 高温 = 85 / 125°C | 常见于 15/16 批次 |
| 低温 = 0 / -25°C | 常见于 05/06/10 批次 |
| 无温度标记 = 常温 | 常见于 01-04/07/09/11-13 批次 |
| 同芯片双温度 | 如 `PDK1_TT10_85` 与 `PDK1_TT10_125` 归并为同一颗芯片 TT10 的两个温度组 |
| **分图不合并** | 每个温度**独立一张热力图**（各自的标题与画布），在同一网页中按序排列，绝不把两个温度的数据画进同一张图 |
| 分图排序 | 低温(0/-25) → 常温 → 高温(85/125)（常温按 25°C 参与排序） |
| 温度展示 | KPI 卡片"测试温度"、每张分图标题（▎ 85°C）、Fail 明细表温度列均会标注 |

## 3. 工具功能原理

### 3.0 模块架构

四个源文件为"**核心引擎 + 三个入口/渲染层**"的分层结构：

```
              ┌──────────────────────────────┐
              │  lb3tools_core.py（核心引擎）   │  唯一的数据源与判定逻辑
              │  · csv / chart xlsx 解析       │
              │  · 良率统计 / 失效分类公式       │
              │  · Shmoo 矩阵 / 向量库扫描      │
              │  · xlsx 报告生成               │
              └───────┬──────────┬───────────┘
                      │          │
        ┌─────────────┘          └─────────────┐
        ▼                                      ▼
  lb3tools_cli.py                        lb3tools_html.py（网页渲染层）
  （命令行入口 + html 脚本入口）                · 复用 core 全部计算函数
  · 均不含计算逻辑，仅做参数传入与转发           · 把结果渲染为单文件 HTML+ECharts
```

设计原则：**core 是引擎，CLI 是方向盘，html 是仪表盘**。新增网页功能对原有文件零侵入（core 未改一行判定逻辑），网页模块故障也不影响 xlsx 报告输出。

### 3.1 error_count 汇总

遍历每颗芯片的全部测试点，输出三张表：

- **总览**：每芯片的测试点数、Pass/Fail 数、失败向量数、最大 Error Count、整体判定；
- **失败明细**：所有失败点的完整信息（芯片/向量/频率/电压/实测VDDL/错误数）；
- **向量统计**：跨芯片视角，每个向量在多少颗芯片上通过/失败、最大错误数——用于发现"某个向量普遍失败"的系统性问题。

### 3.2 Shmoo 矩阵汇总

将每颗芯片的数据聚合为 **(频率 × 电压) 二维矩阵**，每个格点显示 `通过向量数/总向量数`，并做颜色标注：

- 🟩 绿色 = 该 (F,V) 点全部向量通过
- 🟥 红色 = 全部失败
- 🟨 黄色 = 部分通过

同时自动提取窗口参数（**全通过判据**）：

- **Vmin[f]**：频率 f 下全通过的最低电压（低压边界，体现电压余量）
- **Fmax[v]**：电压 v 下全通过的最高频率（速度边界）

支持 `--vector` 子串过滤（如只看 G2 组、或只看 EMC0000 应力），过滤后矩阵仅聚合匹配的向量。

### 3.3 良率统计

**核心问题：在哪个条件下判定芯片好坏？** 流程如下：

```
全部测试点
   ↓ ① 圈定标称点(如 750mV × 20/25MHz)
标称测试点
   ↓ ② 剔除设备侧无效数据点(ClockSetFail/ReadError → 机台/环境问题, 不参与任何判定)
芯片相关测试点
   ↓ ③ 识别系统性失败向量(≥30%芯片 Fail 的向量 → 向量级设计问题, 非芯片缺陷)
有效判定点
   ↓ ④ 逐芯片失效模式分类
   ├─ Pass          全部通过
   ├─ 芯片级失效    Fail点≥90% → 测试通路/芯片级缺陷(如TT45)
   ├─ 分组级失效    某存储器分组Fail≥60% → 该组硬缺陷(如TT30的G2)
   └─ 边缘失败      零星Fail → 向量级速度边缘
   ↓ ⑤ 汇总
严格良率 + 调整良率(剔除系统性向量后)
```

**为什么需要"调整良率"？** 实测发现 `G1_EMC0000`（40/40 颗失败）、`G7_EMC0000`（33/40 颗失败）这类向量在几乎所有芯片上都失败——这是**向量本身的设计/规范问题**，不是某颗芯片的缺陷。严格判定下良率为 0%，剔除后才能反映真实芯片健康度（批次 03：92.5%）。

**ClockSetFail/ReadError 如何处理？** 二者是设备侧无效数据点（时钟源设置失败、电源回读超差），**不参与任何判定**——既不算 Fail（避免把健康芯片误判为失效），也不单独归类为异常。工具仅在日志、总览"设备侧异常"列和同名明细 sheet 中记录它们，供测试人员参考。

### 3.4 标称条件自动探测（auto 模式）

不同批次电压/频率形态不同，`auto` 模式自动匹配：

**电压探测 `auto_nominal_voltage()`**：

- 快测批次（单电压档）→ 直接采用该档；
- Shmoo 批次（多电压档）→ 按 **750→700→800→650→850→...** 优先级选择批次中存在的档位。优先选 750mV 是因为它是芯片标称工作点，避免随机命中 500mV 低压区（本来就测不过）造成"全失败"误判。

**频率探测 `auto_nominal_freqs()`**（在选定电压下）：

- ≤3 个频点（快测批次）→ 这几个频点本身就是标称点，全用；
- >3 个频点（Shmoo 批次，8 个）→ 自动回落到标称频率 **20/25MHz**，即"从 Shmoo 矩阵中只取标称格点判定良率"。

报告中会输出实际采用的判定条件（如 `750.0mV × [20.0, 25.0]MHz`），供核查。

### 3.5 向量库信息（vecinfo）

直接解析 `/LB3/VECTOR/` 下的向量源文件（格式见 1.5 节），提供三项能力：

**（1）库概览**：每个向量文件夹的向量数、总 cycle、最长向量、IO 模式字宽度范围、总 dump 字节；

**（2）分组指纹表**：自动提取每个向量的首行 IO 模式字（即 IO_MODE_SEL 寄存器值），按"存储器分组 × IO 模式字"聚合成指纹表——同分组同算法的向量共享 IO 模式字（如 G0 组基础 March=0xB88E、EMC 变体=0xB884），可用于快速核对向量归属；

**（3）交叉校验（可选）**：提供测试数据（批次目录/csv/chart）时，双向比对：

- 测试数据中出现、但向量库无源文件的向量（需补源文件或核对命名）；
- 向量库中有、但该批次从未测试的向量。

**派生参数**：按 DFT Test Tool 文档公式，从向量行数推导 `dump_bytes = cycles × 16`（失败回读长度）与 `xdma_parts = cycles // 8192 + 1`（加载分包数），见"向量明细"sheet。

**输入合法性校验**：若指定目录中的 .txt 文件没有任何一个首行为 `0x` 开头的 IO 模式字，判定为误指的普通目录（而非向量库），报错退出，避免把无关 txt 当作向量产出无意义报告。

实测（批次 03 vs 向量库）：库中 299 个文件去重后为 171 个唯一向量名（Default/ALGO/EMC 文件夹均为 TEST_FINAL 的子集），批次 03 测试的 171 个向量与库完全一致，双向差集均为 0。

### 3.6 网页测试报告（report）

将批次测试数据生成为**单文件 HTML 看板**（约 1~2 MB，内嵌 ECharts 图表库，双击浏览器打开即看，离线可用），用于数据可视化交付与团队共享。采用**深色科技风**设计（参考公司 DFT 总结页 `Referance_mbist.html`），单页自上而下布局：

| 区块 | 内容 |
|---|---|
| **Header** | 标题 + MBIST 标签（左）/ 数据源、向量数、芯片数、判定条件、生成时间（右） |
| **KPI 卡片** | 6 张：芯片数量 / 测试温度 / 测试点总数 / 全向量 Pass 芯片数 / 存在 Fail 芯片数 / 调整良率（颜色随良率变：绿≥80% / 琥珀≥50% / 红<50%） |
| **Alert 提示框** | 红色关键发现（最差芯片失效占比）+ 绿色通过提示（系统性失败向量数、健康芯片数） |
| **向量分类总结** | 4 张类别卡片（对应《LB3测试进度汇总》：1 个 Mbist_标称 + 3 个 SHM 扫频扫压）：已测/库内总数、全向量 Pass 与存在 Fail 条数、窗口异常向量数；标称卡片附 Default/EMC/ALGO/标称独有 细分；未覆盖类别置灰 |
| **双栏图表** | 左：各芯片 Fail 向量数柱状图（最差芯片标红）；右：芯片级结果构成环形图（中心显良率） |
| **向量×芯片热力图** | **按温度分图**（85°C / 125°C 各一张）；每格=该向量在该芯片的全部测试结果聚合；**鼠标悬停格子展开格内频压明细矩阵**——标称批次显示 2~3 个频压点（750mV×20/25MHz），扫频扫压批次显示 8频率×10电压=80 个小格（列=电压，行=频率，绿/红=Pass/Fail），并统计"格内 X/Y Pass"；明细仅悬停时显示。着色(窗口法)：标称=离散绿/红；扫频扫压=绿=正常窗口(含部分Fail角点) / 琥珀=窗口异常(15MHz低频失效或Fmax@750掉档≥10MHz) / 红=全Fail |
| **测试条件一览** | 静态表格：每颗芯片实际测试的温度、频率点清单（N点）、电压点清单（N点）、标称判定条件——不看悬停即可知道每个批次"测了哪些频率电压" |
| **失败向量 TOP** | 横向柱状图，按失败芯片数排序（系统性失败向量排最前） |
| **Fail 明细表** | 标称条件下全部芯片相关 Fail 记录（向量名 / 芯片 / 温度 / 频率 / 电压），sticky 表头 + 滚动 |
| **Footer** | 数据来源 + 判定条件 + 良率 + ECharts 来源 |

技术要点：

- **ECharts 三级回退**：优先读取工具目录下的 `echarts.min.js` 内嵌 → 无则自动下载并缓存 → 断网时回退 CDN（此时查看需联网）；
- 判定逻辑与 xlsx 报告**完全一致**（复用同一 core 函数），网页与 Excel 结果可互相核对；
- **热力图模式前置选择逻辑**：由 csv 实际频压组合数自动判定——≤3 组（如 750mV×20/25MHz）→ 标称热力图（格子=Pass/Fail 离散着色，悬停显示 2~3 个频压点）；>3 组（如 500-950mV×10-45MHz=80 组）→ 扫频扫压热力图（窗口异常格琥珀标注(悬停显示⚠窗口异常)，全Pass绿/全Fail红，悬停显示 80 小格明细）。可用 `--heatmap-mode nominal/sweep` 强制指定，默认 auto；
- **良率/失效分类只取标称条件点**（扫频扫压批次的角点 Fail 是扫描预期，不计入良率，所以标称全 Pass 的批次 边缘失败/分组级失效=0 是正常口径）；扫频扫压批次的数据总结会额外列出 **"扫频扫压重点异常"**（单格失败率>80% 的向量×芯片格子，如 16 批次的 G1×TT50），这类异常不计入良率但会被显式暴露；
- **两个入口共用同一实现**：`lb3tools_html.py` 直接运行与 `lb3tools_cli.py report` 子命令均调用 `lb3tools_html.run_report_cli()`，命令行参数、控制台输出、报告内容完全一致，修复/增强只需改一处；
- 支持与 yield 相同的 `--nominal-v/--nominal-f`（默认 auto）。

实测：批次 03（40 颗）浏览器渲染验证通过——KPI 92.5% 绿色、环形图中心 37/40、热力图 dataZoom 可交互、失败明细表 910 行、零 JS 报错；多批次生成回归全部通过。

## 7. 判定规则详解

### 7.1 结果类型三分法

（完整定义见 1.1.1 节，此处从判定规则角度归纳。）

工具将 Test Result 分为三类，区别对待：

| 结果类型 | 取值 | 处理方式 |
|---|---|---|
| 通过 | Pass | 计入通过 |
| **芯片相关失败** | Fail | 计入失效判定（良率、失效分类、系统向量识别） |
| **设备侧无效数据点** | ClockSetFail / ReadError | **不参与任何判定**（不算 Fail 也不单独归类），仅记录于日志/总览列/明细 sheet 供参考 |

判定边界：`is_chip_fail()` 只认 `Fail`；`is_equip_fail()` 匹配 `{CLOCKSETFAIL, READERROR}`（大小写不敏感）。若未来数据中出现其他未知结果类型，二者都不匹配，将被忽略不判定（当前实测数据中仅有上述四种结果，不存在此情况；如遇到新类型建议先扩充 `lb3tools_project.py` 的 `equip_fail_values` 词表或明确归类）。

### 7.2 失效模式分类阈值

| 类别 | 判定条件 | 物理含义 | 实测案例 |
|---|---|---|---|
| Pass | 标称点(剔除系统向量后)无 Fail | 健康 | — |
| 芯片级失效 | Fail 点 ≥ 90% | 测试通路/电源/时钟系统缺陷，无修复价值 | TT45（ICL链路先失败、错误计数饱和1000） |
| 分组级失效(Gx) | 某分组 Fail 点 ≥ 60%（且该组点数≥8） | 该存储器分组物理硬缺陷（位线短路/译码器开路等），跨算法跨应力一致失败 | TT30 的 G2 组 |
| 边缘失败 | 其余零星 Fail | 向量级速度边缘（如某EMC向量25MHz测不过、20MHz通过） | TT32 等 |
| 无数据 | 标称条件下无任何测试点 | 判定条件与数据不匹配（如电压选错档） | — |

注：ClockSetFail/ReadError 不影响上述任何类别的判定；若芯片存在此类数据点，其说明中会附加计数（如"全部测试点通过 (+1 个ClockSetFail/ReadError数据点, 不参与判定)"）。

### 7.3 系统性失败向量识别

某向量在 **≥30% 的芯片**标称点上 Fail → 判定为系统性向量（向量级设计/规范问题），在"调整良率"中剔除、单独列表。目的：把"向量的锅"和"芯片的锅"分开。（设备侧无效点不参与系统向量识别。）

### 7.4 Shmoo 窗口参数

- **Vmin** 采用**全通过判据**（该频率下所有向量都过的最低电压），比"部分通过"判据更保守，反映最严苛向量的边界；
- 10MHz 全失败为系统性现象（最小工作频率约束），非缺陷。

### 7.5 扫频扫压异常判据（窗口法，替代失败率阈值）

**为什么不用失败率阈值**：扫频扫压批次的基线失败率天然偏高——10MHz 全向量 Fail（系统性，约 10% 失败）+ 高频 rolloff（物理 Fmax）叠加后，批次失败率中位数可达 50% 以上（实测 16 批次 130 格中 50~80% 失败的有 89 格）。任何固定失败率阈值要么漏报（80% 漏掉 G1 的 10 格中 7 格）、要么误报（50% 把正常物理现象全标出）。

**工具采用的三条物理判据**（扫频扫压模式下自动输出到"数据总结"）：

| 判据 | 规则 | 物理含义 | 16 批次实测 |
|---|---|---|---|
| ① 低频异常 | 某向量 **15MHz 失败率 >50%** | 频率越低越易通过是物理预期（基线失败率 ≤11%），低频大面积 Fail 违反预期 | G1、G3、ROM_G3（15MHz 100% Fail） |
| ② 窗口上沿掉档 | **Fmax@750mV**（最高全通过频率）最低的向量 TOP3 | 单一数值可直接解释"最高只能跑到多少 MHz" | G1/G2/G5 = 25MHz（最好的 ROM_G4 = 40~45MHz） |
| ③ 最差格子 | 单格失败率 >80% | 定位最差点位 | G1×TT50(86%/88%)、G1×TT29(84%) |

**结论口径**：
- 10MHz 全 Fail、45MHz 部分 Fail = **正常物理现象**，不需要优化；
- 低频异常（①）+ 窗口上沿掉档（②）= **需要反馈设计/向量团队核查**的问题（16 批次：G1 最严重，且跨全部芯片/温度一致 → 向量级问题而非芯片缺陷；TT50 边际略差于其他芯片但差异小）；
- 判定"是否需要优化"看**相对基线掉档**，不看绝对失败率。

## 8. 常见问题

**Q1：输入可以是哪些形式？**
批次目录（推荐，递归找 csv）/ 单个 error_count.csv / 单个 chart xlsx。三种都会被自动识别。

**Q2：为什么严格良率是 0%？**
大概率存在系统性失败向量（如 G1_EMC0000 全员失败）。看"系统性失败向量" sheet 和调整良率。这类向量应反馈研发修订向量或测试规范。

**Q3：Shmoo 批次算良率有意义吗？**
有，但样本小（5 pcs）只做参考。auto 模式会自动取 750mV×20/25MHz 标称点判定。注意 Shmoo 批次无 Error Count 信息（chart xlsx 不含）。

**Q4：`--vector` 过滤对 errcount/yield 生效吗？**
不生效，仅 Shmoo 汇总支持。errcount/yield 面向全部向量。

**Q5：文件夹里有"副本"csv 会被误读吗？**
早期数据中存在 `xxx - 副本.csv`，会因同文件夹多 csv 导致芯片覆盖/数据错乱，使用前请清理（项目中已删除 60 个副本）。

**Q6：浏览器打开 HTML 显示空白/加载慢？**
报告文件较大（1~3 MB，内嵌 ECharts 库），部分浏览器（如 360 兼容模式）加载慢或不渲染。解决：换 Chrome/Edge，或用 HTTP 方式打开（`python3 -m http.server 8000` 后访问 `http://localhost:8000/报告.html`）。

**Q7：数据里 ClockSetFail / ReadError 是什么？**
ClockSetFail = 时钟源设置失败，ReadError = 电源回读失败（实测 VDDL 偏差超容差）。二者均为**设备侧无效数据点**，工具不参与任何判定（不算 Fail、不产生异常类别），仅记录于日志输出、总览"设备侧异常"列和"设备侧异常"明细 sheet，供测试人员参考。

**Q8：一颗芯片既有 Fail 又有 ClockSetFail 怎么判？**
类别完全按真实 Fail 判定，ClockSetFail 不产生任何影响，仅在芯片说明中附加计数，不会互相掩盖。

**Q9：输入路径错误 / 目录不是向量库时会怎样？**
工具报错并以退出码 1 结束（不崩栈、不产出垃圾报告）：路径不存在或目录下无 error_count.csv → `FileNotFoundError`；vecinfo 的 `--lib` 指向普通目录（txt 首行均非 0x 开头）→ `ValueError` 提示确认向量库路径。

**Q10：这个工具经过哪些验证？**
- **CLI 与核心逻辑**：全部批次 × 4 项功能（errcount / shmoo 含向量过滤 / yield / vecinfo 交叉校验）回归通过；生成报告可正常打开；边界情况（单 csv / chart xlsx / 显式与 auto 标称条件 / 空频率过滤 / 向量无匹配 / 空数据 / 错误路径 / 非向量库目录）均验证正确。
- **网页报告**：多批次浏览器渲染验证通过（深色主题正常、KPI/饼图/热力图/柱状图/明细表均正确、零 JS 报错）；各批次生成回归通过。

**Q11：热力图为什么大片红？频率/电压在哪里看？**
- 热力图模式由 csv 自动选择：标称批次（750mV×20/25MHz）每格悬停显示 2~3 个频压点；扫频扫压批次（500-950mV×10-45MHz=80点/格）窗口异常格琥珀标注(悬停显示⚠窗口异常)，悬停任一格显示 8频率×10电压=80 个小格明细——**明细只在鼠标悬停该格子时出现**；
- 扫频扫压批次低压/高频角点 Fail 是扫描预期（物理约束），不代表整批失效；**良率判定只取标称条件点**；
- 该批次"测了哪些频率点/电压点"看「测试条件一览」静态表；也可用 `--heatmap-mode nominal/sweep` 强制切换模式。

**Q12：lb3tools_html.py 直接运行和 lb3tools_cli.py report 有区别吗？**
没有。两个入口共用同一实现 `lb3tools_html.run_report_cli()`，命令行参数（-i/-o/--nominal-v/--nominal-f/--vector/--heatmap-mode/--open）、控制台输出、生成的报告内容完全一致，可任选。

**Q13：双温度批次（85/125 或 0/-25）怎么显示？**
每个温度**独立一张分图**（各自标题+画布），在同一网页按 低温→常温→高温 排序，不会把两个温度的数据画进同一张图。温度识别优先级：芯片子文件夹名后缀（权威）> 批次名单一温度标记（兜底）> 无标记按常温；详见 2.4 节。若芯片文件夹无温度后缀且批次名含多个温度，工具会打印警告并按常温处理——请把子文件夹命名为 `<芯片名>_<温度>`。

**遗留说明（已知限制，非 bug）**：
1. 未知 Test Result 类型（非 Pass/Fail/ClockSetFail/ReadError）会被忽略不判定——当前全部批次数据仅含四种结果，如遇新类型需先扩充 `lb3tools_project.py` 的 `equip_fail_values` 词表或明确归类（见 7.1 节）；
2. 同文件夹多 csv 时以最后扫描的为准（芯片名取文件夹名）——使用前确保每芯片文件夹只有一个 error_count.csv，勿留"副本"（见 Q5）；
3. chart xlsx 输入不含 Error Count / Read VDDL 信息（源数据所限），相关列为空；
4. 网页报告的失败向量排行取 TOP 25（避免页面过长），完整清单见 errcount xlsx 报告。

## 9. 移植到其他项目

工具的**分析/渲染逻辑是通用的**，与 LB3 绑定的只有一份适配配置：`lb3tools_project.py`。移植 = 复制 tools_for_LB3 目录 + 改这一个文件。

### 9.1 通用部分（无需改动）

| 部分 | 说明 |
|---|---|
| HTML/CSS/ECharts 渲染 | 深色看板、热力图、悬停明细、卡片，全部数据驱动 |
| 温度分组与分图 | 低→常温→高排序、每温度独立分图 |
| 窗口法异常判据 | 低频异常 / Fmax@750 掉档 / 最差格子（阈值可调） |
| 良率口径 | 标称条件判定 + 系统性向量剔除 + 失效分类 |
| 双入口 / 三级回退 / dataZoom 等工程特性 | 自动继承 |

### 9.2 需要适配的部分（全部集中在 `lb3tools_project.py`）

| 配置键 | 作用 | 什么时候要改 |
|---|---|---|
| `columns` | csv 列名别名映射（必需: vector/clock/voltage/result；可选: read_vddl/error_count） | 目标 csv 表头不同（匹配忽略大小写与空格） |
| `clock_scale` / `voltage_scale` | 单位换算系数（统一到 MHz/mV） | 目标 csv 用 V/GHz 等其他单位 |
| `pass_values` / `chip_fail_values` / `equip_fail_values` | 测试结果词表 | 目标项目的结果取值不同 |
| `chip_name_pattern` / `temp_chip_pattern` / `temp_batch_patterns` | 芯片名与温度提取正则 | 芯片文件夹命名规则不同 |
| `nominal_v_priority` / `nominal_freqs` | 标称条件探测 | 标称工作点不同 |
| `vector_categories` | "向量分类总结"卡片的类别/库总数/匹配正则 | 向量命名体系不同（不改则全部落入标称兜底卡，模块仍可用） |

### 9.3 移植步骤

1. 复制 `tools_for_LB3/` 到新项目；
2. 看目标项目 csv 表头 → 改 `columns` 别名（不改会报错并**打印实际表头**，照着填即可）；
3. 单位/词表/正则/标称条件按 9.2 调整；
4. （可选）改 `vector_categories`；
5. 直接跑 `report`——无需改任何分析/渲染代码。

### 9.4 已验证的移植能力

- 列名别名匹配（忽略大小写/空格）与单位换算（V→mV 自动 ×1000）；
- 缺必需列时 `ValueError` 报错并打印实际表头，指引用户去配置；
- 结果词表驱动 `is_chip_fail` / `is_equip_fail` 判定；
- 向量分类未命中 → 兜底"标称"卡，模块不崩溃。
